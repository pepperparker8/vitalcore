# CLAUDE.md: VitalCore

## Project
VitalCore is a personal health intelligence PWA. It combines training load, sleep, daily psychology check-ins, body measurements, blood markers and injuries into one readiness score and an AI-generated daily briefing.

Current version: **7.0**. Built iteratively in claude.ai as an artifact. This repo is the move to a standalone, deployable app.

## User context
- Invite only (v124): the owner and the people the owner invites in Supabase; each person sees only their own data. Personal notes about the owner (devices, phone, habits) live in the gitignored `CLAUDE.local.md`; never put them back here, the repo is public.
- Sports: running, cycling (e-bike too), hiking, weights, yoga, swimming (distance in metres).
- Android Chrome first. Minimum viewport 360px.
- Polar, connected since v116 through the owner's own backend (Polar AccessLink V4; a direct browser call was 403, so the OAuth tokens live in Vercel functions, repo `vitalcore-backend`, one token row, so the owner's only). Polar supplies the detailed night; Intervals.icu stays the source of daily wellness (HRV, resting HR, breathing) and of the readiness score. Polar's own recovery verdicts are not imported.
- Intervals.icu wellness can mix two devices (a watch for the day, a ring or band for sleep), which is why the Body resting heart rate baseline uses all imported values rather than one device.
- Training data: Intervals.icu (CTL, ATL, TSB, PRs).
- Blood markers in **mg/dL**, never mmol/L.
- AI: Anthropic Messages API with each user's own key.

## Architecture
- Vanilla HTML/CSS/JS, no framework, no build step. Hosted on GitHub Pages; Supabase for sync (local-first, RLS own rows).
- Layout: `index.html` (shell), `css/app.css`, `js/` classic scripts sharing globals, loaded in this order: core, sync, strength, log, today, settings, render, recovery, detail, chart, form, trends, progress, plan, coach, sessions (v121), workout (v122), strategy, fuel, health, digest, insights, app. Top-level names are shared across all of them and the tests page, so a new global must not reuse one. `sw.js` caches the shell (add new files to SHELL and bump the cache name).
- Tests (v118): `tests/index.html` loads the app scripts (all but app.js, which starts the app) and runs the Spec v2 acceptance tests in the page, no library. Open it over a local server (`.claude/launch.json` "vitalcore": `python3 -m http.server 8118`, then `/tests/`); it shows "N of N passed" and sets `window.TEST_RESULT`. It stubs `Storage.prototype.setItem` before core.js and replaces `save`, so fixtures never reach the app's storage. Not in `sw.js` SHELL; never cached or shipped to the phone. Since v126 `/tests/?day=YYYY-MM-DD` runs the whole suite as if today were that date (a `Date` subclass offset to that day, so the clock still moves) and `atDay(dt, fn)` runs one block on a frozen day; run it on a few weekdays before a release that touches the outline.
- External: Google Fonts only (IBM Plex Mono, Outfit, DM Serif Display).
- State: one in-memory object `_s`, accessed via `S()` and written via `save(d)`, which triggers a 400ms debounced persist.
- Charts: hand-drawn on `<canvas>`. Since v119 every time chart goes through `mountChart()` in `js/chart.js` (the old `lineChart()` was removed in v89): Trends `formCanvas`, `tsbCanvas`, `readCanvas`, `hrvCanvas`, `rhrCanvas`, `respCanvas`, `moodCanvas`, `sleepCanvas`, `wtCanvas`, `bodyCanvas`, `mindBars`, `trainBars`, `strCanvas`, `spBars`, `boCanvas`, `ldCanvas`, `prCanvas`; Health blood charts `btc_<marker>`; the detail sheet `dtChart`. The workout sheet's trace chart (v122, `#wkTr`, `wkDraw` in workout.js) is its own canvas on elapsed time, not `mountChart`. Canvas colours come from `cssv('--name')`, so they follow the theme; `chRedrawAll()` redraws every mounted chart when the theme changes (`setTheme` and the system dark-mode listener). Readiness is snapshotted daily in `readHist` (local only). Sets per muscle (strength.js) stays DOM category bars, with the `TH.SETS_LO`/`TH.SETS_HI` zone.

### Key logic
- `calcReadiness()`: sleep score base (`slScore()`: the logged score, else estimated from time asleep vs goal, goal = 85), adjusted by TSB (positive adds, negative subtracts; v89 fixed the sign), blended 70/30 with latest check-in (sleep and check-in only count when from the last 3 days), HRV and resting HR nudge vs your 30-day baseline (`recoveryAdj()`, only with 7+ days of data), minus 8 per injury severity level, minus 4 per soreness level above mild (check-in `soreness`). Clamped 20 to 100. Since v118 this is the "old readiness": it runs alongside Body for 14 days and is retired once Body is live (see the v118 section); it is not changed.
- `calcBurnout()`: since v118 psychological only: risk = 100 minus the mean of energy, mood and calm over the last 7 check-ins (0 to 100); low under `TH.BURNOUT_MOD`, high from `TH.BURNOUT_HIGH`. Training fatigue is read under Load (`calcLoad`), not here. Read through `calcMind().burnoutHigh`.
- **Stress is inverted** everywhere it feeds a score: 1 = calm (good), 4 = very stressed (bad). Always use `5 - stress`.
- Log > Workout is one form (v83; the separate Quick workout card is gone, do not bring it back): type grid, duration chips (`renderDurChips`), distance, then a collapsed "Date, effort and note". Above the form: "Last 7 days" list with Edit / Delete on every row (`wkRow`, `renderWkLog`, `delWorkout` with Undo that removes the tombstone). Intervals.icu rows carry a source tag. Deleted Intervals.icu workouts, sleep nights and weights stay deleted: `del()` records imported ids (`icu-`, `sl-`, `mi-`) in local-only `gone`, checked on import with `isGone()` (the tombstone alone is cleared after the cloud delete). `put()` clears a tombstone for the same record, so Undo and re-saving are safe.
- Duplicates (v83): `findDups()` pairs a hand-logged workout with an Intervals.icu one of the same type and date (last 30 days). `dupHTML()` shows a strip in Log and in Today's list: "Combine into one" (`mergeDup`: keeps the Intervals record, copies effort, note, sets) or "Keep both" (`keepDup`, stored in local-only `dupOk`).
- AI briefing (v83, `js/insights.js`): one briefing, no Weekly/Monthly toggle. `insightData()` builds today / week / month / trend / health / profile JSON; `INS_SYS` is the system prompt; reply is forced to JSON with structured outputs (`output_config.format` json_schema, `INS_SCHEMA`), falling back to a plain request and `parseInsight()` if rejected. Since v119 it runs at `output_config.effort:'low'` and streams (see the v119 section); `max_tokens` is 8000 (thinking tokens count toward it; 1600 once caused the cut-off "not in the expected format" error), and the one retry after a parse failure uses effort 'medium' and 16000. Sections are listed in `INS_SECS`; old history entries still render. Failures show a plain reason plus `buildFallback()`.
- Briefing memory and follow-ups (v85): `insightData().previousBriefings` (`insPrev()`, last 3 before today) lets the model check its earlier advice in the `followup` section ("Since the last briefing"). The model also returns 3 `questions`, shown as chips under today's briefing with a free-text box (`insQaHTML`, `askInsight`, system prompt `INS_QA_SYS`, shared rules in `INS_COMMON`, plain-text answers, max 10 per briefing). The thread is stored on the briefing as `qa[{q,a,ts}]`, so it syncs inside the existing `rendered` JSON. Regenerate replaces the briefing only on success and keeps the thread. The phone keeps 365 briefings (`insCap()`; 60 with `insLean` after a storage-full save); sync pulls the newest 30 in full (newer `ts` wins, unsent local edits win) and older ones only when missing. History shows 20 at a time.
- Briefing data also includes 12 weekly trends (`insightTrends`), recovery drivers, all blood results with change (`insightBlood`) and code-computed Pearson correlations (`insightCorrelations`, needs `TH.CORR_MIN_N` = 14 paired days since v118, was 8; includes coffee cups vs that night's sleep and previous-day load vs soreness). Model must not diagnose.
- Weekly plan (`js/plan.js`, stored in `profile.plan`): planned vs done per weekday; `suggestWorkout()` follows it when readiness allows and bends it (with a reason) when not. Trends has the weekly training load chart (`renderLoad`, since v119 weekly bars on `mountChart` (`ldCanvas`) with the 4-week average and "Big jump" / "Too fast" lines at `TH.RAMP_CAUTION` / `TH.RAMP_HIGH`; the tapped week shows its sport breakdown) and the Progress & PRs chart (`js/progress.js`, `prCanvas`, PR `marks`).
- Today's session and 7-day outline (v86, `js/strategy.js`): `strategy()` returns 7 days starting today, each `{role, type, lo, hi, effort 1-5, name, how, why, bent}`, computed in code (the AI only explains it). `stWeek()` picks the week mode and minutes target from the 4-week mean: Building x1.07 when 7-day readiness is 65+, Holding steady, Recovering x0.85 (readiness under 50 or high burnout), Easier week x0.75 after three full weeks (since v126 full by training minutes only), Taper / Race week from `racePhase()` (since v118 the 7-day mean is of the hero score, `heroHist()`, against `scoreCuts()`, and high burnout comes from `calcMind()`; form no longer bends today, only the verdict, symptoms, soreness 3+ and a hard day yesterday do). With a weekly plan it follows the plan (notes like "tempo", "long", "easy" set the role) and bends today for a bad or warn verdict, soreness 3+, a hard day yesterday, injuries; without a plan it schedules from usual training days per week. Hard days never back to back, max two per 7 days, none with a moderate injury or under 4 logged workouts. `suggestWorkout()` is now a thin wrapper (day 0, null once trained). The Today card `#sugCard` ("Today's session" / "Next session, tomorrow", `renderSuggest`) was removed in v115 at the owner's request; do not bring it back without asking. The outline lives on Insights only: card `#stratCard` (`renderStrategy`). Briefing data carries it as `today.prescription` and `strategy`. Since v121 each training day also carries a session from the library (warm-up, main set, cool-down with targets), levels, comebacks and swaps; see the v121 section.
- Fuel plan (v87, `js/fuel.js`; the Today Fuel card `renderFuel`/`#fuelCard` was removed in v112 at the owner's request, do not bring it back without asking; the numbers now only feed the briefing): `fuelPlan()` computes protein, carbs and fat in grams from the latest logged weight, today's training (logged workouts, else `strategy().days[0]`) and `profile.nutGoal` (`keep` default, `lose`, `build`; Settings > Food goal). Carbs 3 to 8 g/kg by day level (rest, easy, mod, hard, big, race; at least 7 the day before a race; minus 1 when losing, plus 0.5 when building), protein 1.6 to 2.0 g/kg, fat fills the rest of the day's estimated energy use (v88; clamped 0.6 to 1.5 g/kg). After a session: 0.3 g/kg protein plus 0.5 or 1.0 g/kg carbs. Food portions come from the built-in `FU_FOODS` table (Indonesian staples). Never adjusted by blood results. The briefing gets the numbers as `insightData().nutrition` (null without a logged weight).
- Food log and next-session fuelling (v88, `js/fuel.js`): Log > Food (`#lFood`) keeps one running calorie total per day with quick-add chips and optional protein (`addFood`, `resetFood`, `renderFood`; one record per day, id `fd-<date>`, so two devices merge). Meals came in v98 (see below). Estimated use = `fuRest()` (Mifflin-St Jeor from weight, height, age and `profile.sex` 'm'/'f'/unset = average, x 1.35 for daily living) plus training (`fuWk`: Intervals.icu kcal minus the resting share, else MET table `FU_MET` x minutes; strength minutes from sets via `fuMin`). It is an estimate: there is no all-day activity data. `fuelPlan().week.low` flags "eating too little" when 3+ of the last 7 logged days average 500+ kcal under use (800 when losing), and `fuNext()` gives advice before and during the next big session (today's if not yet done, else tomorrow's; carbs 1 g/kg before, 1.5 for a race; 30/45/60 g an hour by duration). Briefing data: `nutrition.estimatedUseKcal`, `eatenToday`, `lastWeekLogged`, `nextSession`. Sync: table `food_logs` (`docs/supabase-v88.sql`); `TBL.food.opt` makes sync skip it without failing when the table is missing (`noFoodTbl`, note `#fdCloud`).
- Coach card (`js/coach.js`, `renderCoach`, on Insights under the briefing): since v90 it is only "Things to watch" (`coachFlags()`), plus Plan this week and Load this week rows and a "based on N of 14 days" note. `coachVerdict()` (Train / Hold steady / Rest; since v118 the hero score alone sets the level against `scoreCuts()`, and only two gates override it: a severe injury or a systemic illness gives Rest, a mild illness caps the day at Hold steady; flags, form and burnout explain, they no longer trigger) still sets the strain gauge target range and the week mode; the Today verdict strip that showed it (`renderVerdict`, `verdictHead`, `#verdictCard`) was removed in v113 at the owner's request. ## Conventions
- Durations always hours + minutes via `fmtDur()` / `fmtHM()`. Never decimal hours in the UI.
- Check-in uses face icons, never numbers.
- Plain English labels ("How Fresh You Are", not "TSB") with a "Why this matters" expandable for the technical term.
- Validate inputs against physiological ranges with a friendly toast, never a silent save.
- Empty states always explain what to do next and link to the fix.

## Do not reintroduce
Duration/HR fields for weight training, decimal sleep hours, numeric check-in buttons, "Rest day" label for unlogged days. (The old "no Polar connection" rule was lifted by the owner in v116; Polar's own recovery score still stays out.)
